# hff: findings from the review of the two unmerged branches (2026-10-19)

For Andrew, to decide what is approved. Companion to `2026-10-19_unmerged_branches.md`, which has the commit-by-commit detail.

**How these were checked.** Everything below comes from reading code and git history on `main` (tip 0219028 when read). Nothing was run, built or tested, so every statement about what "happens" is a reading of the code, not an observation. Where I could not tell, I say so.

**What "production" means here.** The SRBench entry, `srbench_submission/algorithms/hff-sr/regressor.py`, which drives `notebooks/hff_sr_engine.py`. The experiment scripts in `notebooks/` are not production.

The two branches hold 14 commits that were never merged. Several of them fix or add things that main does not have. Failures come first, ordered by how much they can hurt a production run.

## 1. A production fit may hang forever inside sympy, with no way to stop it

**(a) What is wrong.** Main still calls sympy's `simplify` and `lambdify` on model expressions in several places with no time limit; sympy can spin for hours on certain expressions and cannot be interrupted from Python.

**(b) On main, affects production?** Yes, the code is on main and on the production path. Effect would be a hang: a fit stops producing output and keeps one CPU busy. I cannot say how often it happens. Evidence that it has happened: main's own commit ff1f023 describes a real 2h20m stall on the power-plant seed 23 run (that one is fixed for four call sites). The branch commit 9097cc5 says a `lambdify` stalled "3+ days of CPU" in a wild sweep; that is a code comment in the commit, not something I could confirm.

**(c) Evidence.**
- Still unbounded on main: `notebooks/_sympy_to_karva.py:311` (`sp.simplify`, only on sub-trees of at most 10 nodes, per `_gene_decompose.py` `sub_h=10`, so the risk is limited to awkward nestings such as exp(exp(x))); `notebooks/hff_sr_engine.py:2347` (`sp.lambdify` in `predict`, which SRBench calls on the final model), `:2864`, `:3332`, `:3493`; `notebooks/hff_geppy_helpers.py:1535`, `:1607`, `:2008`, `:2228`, `:2232`.
- Already protected on main: `python/hff/sr/bounded_simplify.py:258` `capped_simplify`, used at `hff_sr_engine.py:2926` and `:3448` and `hff_geppy_helpers.py:1789`, `:1907` (commit ff1f023).
- Branch commit 9097cc5 adds `bounded_simplify`, `bounded_lambdify`, `bounded_nsimplify` (SIGALRM, 5 s) at nine call sites.
- Caution: main's own note at `bounded_simplify.py:14-15` says a SIGALRM timeout does not reliably stop sympy's native code. The branch's approach has the same weakness, and `capped_simplify` itself uses SIGALRM (`:233-248`).

**(d) How sure.** By reading only. Sure the calls are unbounded. Not sure they hang on production inputs; the only direct evidence is the earlier incident and a commit comment.

**(e) Fixing it.** Medium. Route the remaining calls through `capped_simplify`, and give `lambdify` an equivalent guard. The better fix is to stop using sympy for evaluation at all (the engine already evaluates through fuller at `hff_sr_engine.py:3331`). Then reproduce on the stalled seed-23 hall of fame (`seeds/math_s23.hof.json`) to confirm it is fixed. Do not copy the branch code as it stands: it duplicates `capped_simplify` and uses the less safe method.

**(f) Risk of leaving it.** A silent multi-hour hang in an SRBench run, discovered only when the run is late. Rare but expensive, and already seen once.

## 2. The saved hall of fame of a finished fit can be overwritten by the next fit

**(a) What is wrong.** After a fit, the best chromosomes are saved to a file whose default name contains only the random seed; any later fit with the same seed writes over it.

**(b) On main, affects production?** Yes. It does not change the reported model or its score. What is lost is the saved hall of fame of the earlier fit, which the replay and diagnosis tools read (for example `_hof_dataset.py`, the rule bench). The production regressor does not set `HFF_HOF_DUMP`, so it uses the default name; SRBench runs many datasets with the same seeds, so each dataset's file replaces the previous dataset's. The default folder is `/tmp`, which is also cleared by a reboot.

**(c) Evidence.** `notebooks/hff_sr_engine.py:2146-2156`: path from `HFF_HOF_DUMP` or `/tmp/hff_hof_seed{random_state}.pkl`, opened with `"wb"`. `grep HFF_HOF_DUMP` finds no setting in `srbench_submission/`. Fix on branch: commit f9d4854, engine part, 11 lines: if the file exists, write a timestamped sibling and print a loud message.

**(d) How sure.** By reading only. Sure of the overwrite. Not verified that two production runs actually collide on one machine.

**(e) Fixing it.** Small: the 11-line engine change applies cleanly in spirit, but the file now conflicts with the branch's other edits, so it is a hand port of one hunk. Better still, put the dataset name in the file name. The branch's timestamp fallback keeps the old file, which is what the project rule asks for.

**(f) Risk of leaving it.** Evidence from finished runs is destroyed without notice. Costs a re-run when someone needs the earlier hall of fame.

## 3. Production still lets the search use exp, log and tanh freely (commit fcb86ad is NEEDED)

**(a) What is missing.** Main has no way to leave out the exp, log and tanh functions, which the commit measured to be "universal approximators" that fit data without recovering the law.

**(b) On main, affects production?** Yes, in result quality, not in crashes. The commit's evidence is that near-miss models were towers of `tanh(exp(log(...)))` with the wrong structure, so the constant snap could not recover the law. That diagnosis and its counts (tanh in 1 of 120 Feynman truths, log in 0, exp in 10) come from the commit message; I did not reproduce them.

**(c) Evidence.** `hff_sr_engine.py:674-683` registers exp, log and tanh for random sampling unconditionally; `HFFSRConfig` (`:420`) has no `physics_pset_strict` or `allow_exp` field. Branch commits fcb86ad (adds `physics_honest_pset`, `allow_exp`) and bc491e0 (renames to `physics_pset_strict`).

**(d) How sure.** By reading only, that main lacks the option. The claim that dropping them helps is the commit author's measurement, which I did not see or re-run; there is no script for it in the commit.

**(e) Fixing it.** Small to port (about 30 lines in `_build_toolbox` and the config). The decision is not small: the commit makes it the default, which would change what the production entry searches. Port it default-off, then measure on a Feynman and a wild set before turning it on.

**(f) Risk of leaving it.** Nothing breaks. The cost is the lost chance of those law recoveries, and finding 4's scripts cannot run without it.

## 4. Three experiment scripts crash on start

**(a) What is wrong.** Three scripts on main build an engine configuration with settings that no longer exist on main, so they stop immediately with a `TypeError`.

**(b) On main, affects production?** No. They are not part of the production path and nothing imports them (I searched; no file refers to them by name). They are hand-run experiment drivers, so I cannot say who runs them or whether anyone has tried since September; they were committed on 2026-09-18 in a7b9e26 ("the sweep drivers the ignore rule was hiding").
- `notebooks/_nearmiss_phase1.py`: tests the exp/log/tanh removal on the five Feynman problems that came close but missed (I_6_2, I_6_2b, I_9_18, I_10_7, I_11_19), with and without the end-of-run fold.
- `notebooks/_i_9_18_lever.py`: tests how strongly the model-size penalty should push, on the Newton gravity problem I_9_18, one setting per run.
- `notebooks/_measure_select_test.py`: asks which structural measures make the equivalent-form chooser (`eclass_extract_hff`) pick the most law-like form; a request from the fuller team.

**(c) Evidence.** Each builds `HFFSRConfig(...)` with `physics_pset_strict`, `allow_exp`, `b_in_hff`, `lean_hff_vec`, `elite_denoise_to_intake`, `fold_denoise_at_end` or `simplify_winners` (`_nearmiss_phase1.py:120-135`, `_i_9_18_lever.py:69-76`, `_measure_select_test.py:162-164`). Main's `HFFSRConfig` is a plain dataclass without them (`hff_sr_engine.py:420`; zero matches in the file), and Python rejects unknown arguments to a dataclass.

**(d) How sure.** By reading only; I did not start them. Very likely, because the rule for dataclasses is certain and the field names are absent.

**(e) Fixing it.** Small if the fields are added (finding 3 and the WIP items below), small if the arguments are removed from the scripts, trivial to delete the scripts. Which one depends on whether those experiments are still wanted.

**(f) Risk of leaving it.** No production risk. These are broken tools that look working; the lever experiments cannot be repeated. They also show that the branch features were used in experiments whose results are not stored.

## 6. Things on the branches that should not be taken

Listed so nobody takes them by accident.
- Removing the time limits (commit 46f5245). Main's SRBench entry stops on time and says so (`regressor.py:115-125`).
- Replacing "no model" with the hall-of-fame fallback (46f5245, "Edit 6"). Main deliberately reports a failure loudly (`hff_sr_engine.py:3166-3173`).
- The end-of-run fold into gene 0 (2776edf). Main already folds after the snap (`_fold_op.py:35`, engine `:3550-3589`).
- A global switch-off of numeric warnings in the engine (bc491e0).
- Fourteen scratch scripts committed into `notebooks/` instead of `tmp/` (bc491e0, 2776edf).
- Every `gamakAST` import: the package is now `fuller`, and the branch code swallows the missing import, so it would silently do nothing.
